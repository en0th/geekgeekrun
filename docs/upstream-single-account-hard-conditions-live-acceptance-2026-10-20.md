日期：2026-10-20。分支：`codex/upstream-p1-fixes`。本机 macOS、Electron 39.2.7、Chrome 155，版本号保持 `0.22.1`。

**修复后 13 组真实 BOSS 只收集验收全部通过，预览与实际执行一致；全程 0 开聊、0 不合适标记。** 公司规模、学历、行业、融资阶段、全职/实习/兼职、日薪/时薪及缺失字段均有真实样本。继续使用现有单账号，没有合入多账号分支。

## 方法与样本

使用应用现有 CLI 入口、单账号队列和实际 BOSS 页面顺序运行。每组冻结完整配置，使用 `collect` 和「只收集符合求职条件的岗位」，限定请求、详情、运行时间及换源次数。取样阶段另用「只收集全部岗位」确认站点原始字段。没有调整原有停留和休息节奏，没有运行消息跟进任务。

每条验收证据对应实际查看的岗位 ID，记录页面选中行、可见详情、API 岗位/公司字段、网页已应用筛选和执行判定。随后用生产职位库查询引擎读取同一岗位，把同一配置交给渲染器实际使用的 `evaluate`，比较预览和执行结果。最终 13 条判定的薪资、类型、学历、规模、行业、融资字段与页面原始证据也逐项一致。预期结果和拒绝原因另外逐组断言，避免仅以两个实现互相一致作为通过依据。

主要样本：

- 实习岗位：`200-250元/天`、本科、500–999 人、其他专业服务、不需要融资，详情 `jobType=4`。
- 全职岗位：`6-11K`、大专、100–499 人、日化，详情 `jobType=0`。
- 兼职小时工：`20-30元/时`、学历不限、10000 人以上、互联网、C 轮，详情 `jobType=6`。职位库另有 `25-30元/时` 的同类真实样本。
- 融资信息缺失的实习岗位：`170-200元/天`，原始 `stageName` 为空。

薪资沿用区间有交集即通过的规则。例如要求 25–30 元/小时，20–30 元/小时存在交集，因此通过；公司人数则要求岗位给出的整个区间符合。日薪与时薪不相互换算，也不换算为月薪。

## 实测发现并修复

1. **详情类型编码与网页筛选编码不同。** 真实详情的 0/4/6 分别对应全职/实习/兼职，网页选项则是 1901/1902/1903。补充已验证的详情编码及旧数据迁移；优先使用明确的中文字段。不从岗位标题、日薪或时薪猜测类型；未确认的编码继续按信息不足处理。迁移只填充缺失标签，读取最近保存的 API 记录，无法解析则不补全；保留已有明确标签和原薪资。
2. **网页求职类型下拉仅悬停时可能仍隐藏。** 增加点击展开和可见选项等待，按文字选择，并核对选中态或实际筛选参数。真实实习、全职、兼职任务分别确认页面参数为 1902、1901、1903。
3. **「只收集符合条件」仍会提前保存预载或拒绝的详情。** 初次实测任务 #13 收集数为 0，却新增了 1 个唯一岗位。该模式现在关闭筛选前的网络和详情保存，改在所有条件通过后等待入库成功，再发布已收集事件并计数。修复后全部负例均没有本轮观测或首次发现记录。「只收集全部岗位」和正常浏览继续保留原有捕获行为。查看日志改为「已查看」，避免把查看等同于已入库。
4. **预览的操作文案与只收集模式不一致。** 只收集预览现在只显示「可收集」或「跳过」；不建议发送、标记或冷却。「只收集全部岗位」的预览与实际执行一样忽略求职条件。
5. **预览函数没有界面入口。** 在第 2 步补上「预览筛选结果」，按需读取职位库最近 100 条，展示实际字段、原因和计划操作。首次桌面检查又发现 IPC 分页结果有一层封装，已修复读取层级，并按真实返回结构修正回归夹具。
