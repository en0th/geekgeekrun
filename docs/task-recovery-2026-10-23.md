# 暂停、继续与异常处理改进

日期：2026-10-23。沿用「把复杂留给系统，把下一步交代清楚」的界面原则，分批验证并合并。

## 第一批：先保证「继续运行」确实可以继续

复核发现，发送结果未知虽然禁止外层自动重启，但检查点仍可出现在「已暂停」中，并提供普通继续入口。另一处只依赖任务快照文件检查运行方式；该文件缺失时，不能据此保证只收集任务不会变为打招呼。

本批补齐：

- 真正点击沟通按钮前，同步保存 `messageSendPending: true`；BOSS 确认且开聊记录写入成功后才解除。状态写入失败会中断后续点击；手动暂停、窗口关闭和进程意外结束不会清除未确认状态。
- 退出码和待确认标记进入检查点。新界面与主进程共同判断是否可以继续；旧检查点结合对应运行的历史记录判断，其他任务及复用编号的旧历史不会改变本次判断。
- 主进程在更新任务配置和派发 worker 前核对检查点及原运行方式。即使配置快照文件缺失，也不能将原只收集任务继续为打招呼。
- 待确认任务显示「先核对上次发送结果」，提供「去 BOSS 核对」和「结束本次任务」，保留数据，不提供直接继续按钮。打开的是 BOSS 会话页，不执行打招呼或标记。
- 模式变化、无法确认的旧打招呼检查点和异常元数据会给出提示，保持停止；明确为只收集的旧检查点继续保留恢复能力。
- 已完成的任务不作为可继续任务；运行中的任务和排队任务仍沿用现有执行方式。

### 验证范围

两端类型检查、完整回归及生产构建按每批最终提交执行。回归覆盖真实检查点文件的重新读取、写入失败时不点击、确认存储失败时保留待确认状态、UI 和主进程拒绝不安全的继续、快照文件缺失时的运行方式校验，以及既有公司身份/岗位 ID 的最终发送前检查。

使用真实 renderer 生产构建和本机 Chrome，配合隔离的合成 IPC 状态，检查普通只收集暂停、发送待确认、模式变更、任务详情及重新加载后的入口。界面验收未启动真实任务、未访问 BOSS，没有真实发送或标记，不计作 Windows 实账号现场验收。

原工作区的运行方案和其他并行改动保留，本批在隔离工作树上实现。

## 第二批：每种停止状态都给出下一步

主页面、任务详情、任务列表和停止通知使用同一套恢复说明：先说为什么停下，再说明下一步。运行说明和技术细节按需展开。

| 状态 | 用户看到的下一步 |
| --- | --- |
| 手动暂停 | 继续当前任务，累计统计和用量保留 |
| 任务窗口正在等安全验证 | 切换到任务浏览器完成验证，完成后自动继续，无需重新开始；不另外打开不同会话来替代验证窗口 |
| 登录失效或账号变化 | 进入登录设置，使用这次任务的原账号，处理后再继续 |
| 来源不可用、页面筛选未确认 | 直接展开对应来源或筛选区域；只定位控件，不自动修改条件 |
| 达到运行上限 | 调整上限；只有当前上限足够容纳已有累计用量时才显示继续入口，用量不会清零 |
| 浏览器或网络异常 | 检查浏览器设置或BOSS页面，确认可用后继续 |
| 任务服务暂时不可用 | 保留上次已知状态，重新读取；服务恢复后自动更新状态，仍不启动或继续任务 |
| 数据或任务进度无法读取 | 保留上次已知状态，提供重新读取和数据目录入口；不把读取失败当成没有任务 |
| 发送结果未知、保护检查拦截 | 保持停止，先核对BOSS结果或反馈问题，不提供普通继续 |

### 操作和状态保持一致

- 暂停时底部主按钮处理当前任务；「新建任务」单独显示，开始前仍需确认，避免误开新任务重置累计值。
- 切回原运行方式只改只收集/打招呼选择，保留城市、薪资、来源等条件；开始前和主进程仍核对原方式。
- 继续前重新读取任务状态，携带明确的运行编号。读取后发现任务已更换、派发期间检查点刷新或停止通知迟到，都不能把另一任务的状态和计数套用过来。
- 任务服务和检查点一起核对；监听实际变化的状态值，避免新数组引用造成重复刷新。真实 Vue 回归覆盖启动和历史长度不变时的更新。读取请求按顺序处理，失败时保留上次状态；重试成功后才解除限制。读取失败时不能新建、继续或结束尚未确认的旧任务。
- 暂停和继续的准备阶段防止重复点击。消息跟进的重新开始与找岗位的继续分开，不交叉操作。
- 损坏或不可读的进度文件抛出不含文件内容的提示，保留原文件；新建任务不能先删掉无法读取的检查点。发送前的严格状态写入或结束记录核验失败，会按数据错误停止，不进入通用浏览器重试。
- 已停止不等于已被用户终止。任务记录仅对明确终止的运行显示「已终止」。

### 第二批验证

定向回归覆盖停止原因到操作入口的映射、上限边界、原方式恢复、进度读取失败及重试、连续点击、迟到停止通知、明确运行编号和原文件保留。本批本地两端类型检查、514 项完整回归（0 失败、0 跳过）通过；生产构建及线上平台检查均以本批最终提交为准。

界面覆盖 13 种停止/异常场景、运行中的服务连接恢复，以及窄窗口下的主操作可见性。仍使用真实 renderer 配合合成 IPC 状态；只检查界面和路由，不接触实际BOSS账号。筛选、只收集、累计用量和任务执行的既有回归继续作为合并门槛。

## 第三批：Windows 浏览器启动与诊断

第二批合并后的 master 检查在 Windows 启动 Chrome 时失败，约 30 秒后返回浏览器不可用，尚未进入岗位页面。旧报告没有保留具体的启动阶段原因，无法据此断言 Chrome 失败的根因。

任务浏览器改用 Puppeteer 支持的 `pipe` 连接，去掉对 Chrome 输出 WebSocket 调试地址的依赖；任务独占浏览器进程，没有通过调试地址重连的调用。项目锁定的 Puppeteer 24.19.0 已支持此选项，连接方式见 [Puppeteer LaunchOptions](https://pptr.dev/api/puppeteer.launchoptions)。继续使用有界面的真实 Chrome、独立会话和后台最小化窗口；无法确认窗口状态时仍关闭并暂停。

启动超时使用单独的诊断原因 `launch-timeout`，让用户知道需要先检查浏览器再继续。诊断只保留阶段和原因，原始启动报错中的路径、调试地址、账号信息不会进入日志。Windows 真实浏览器检查记录每次启动的耗时和连接方式，失败时保留安全的原因和操作提示；同时验证实际连接没有 WebSocket 地址。

本批继续要求两端类型检查、完整回归和线上 Windows 实际窗口检查通过。筛选命中/排除、只收集入库、0 发送、0 标记、窗口关闭后的停止及发送结果未知保护均保留。离线 CI 使用隔离浏览器和合成岗位，不代表 Windows BOSS 实账号现场验收。
