## 补齐现场证据

验收记录器仅在显式指定 `GEEKGEEKRUN_COLLECT_AUDIT_DIR` 时启用，并拒绝打招呼模式。本批补充：

- 读取公司页及 Nuxt 包装组件的真实选中岗位、品牌、原生筛选、页码和登录状态；普通列表的记录继续保留。
- 在恢复 Cookie 和导航之前，给所属任务页面安装沟通及不合适标记请求的额外阻断；保留代理直到该页面关闭。消息未读数等读取继续正常工作。
- 区分通信相关读取和发起沟通、发送、标记请求，不把读取当成已发送。记录不包含请求地址、参数、请求头、Cookie 或消息内容。
- 记录首次查看岗位前的接口状态、数值返回码和数据结构；JSON 无法读取时保留失败分类，不保存原始响应或错误正文，也不改变原有停止判定。
- 意外出现发送或标记进度时，记录为验收失败。

新增六项回归覆盖启用边界、阻断安装失败、页面关闭清理、读取与写操作区分、公司及普通页面取证，以及包含敏感字符串的响应不会进入证据。

后续对照使用官方 [Chrome for Testing](https://googlechromelabs.github.io/chrome-for-testing/) 稳定版 Windows x64，版本和下载校验保存在本机；仍按正常登录和任务入口操作，现有来源、身份及访问守卫继续生效。

原始登录凭据、页面内容、数据库和测试日志只保存在本机，不提交到仓库。线上 CI 的真实窗口检查使用离线页面，不能据此将上表尚未通过的现场项目标为通过。

## 第二批：修复导航等待并完成现场验收

Chrome 156.0.8078.47 正常登录对照显示：账号接口可正常返回有效身份；安全检查导致主文档重新加载时，旧列表请求保留了 HTTP 200 响应头，但正文没有完成。新文档随后正常返回 15 条列表和岗位详情，页面已经可操作，`document.readyState` 仍为 `interactive`。旧的完全加载要求和旧响应正文等待会把这次正常换页误判为访问状态不明。

修复包括：

- 按 DOMContentLoaded 导航，确认可交互或完全加载状态、预期岗位地址、有效账号，以及真实职位工作台模型；仍等待来源和筛选的后续确认，不以地址或文档状态单独授权入库。
- 通过 CDP 主框架 `loaderId` 确认完整文档替换。替换后清除旧列表快照并释放旧正文等待；同文档筛选变化和子框架导航不走这条处理。
- 当前文档的不可读正文、格式错误、来源不符和访问限制继续停止。已经确认的访问失败不会被导航清除，旧请求迟到的明确登录失效或限制响应也继续阻断。
- 文档监听初始化有上限，无法建立时沿用严格响应检查。停止任务会解除所属监听，不改变其它页面。

五项新增回归覆盖可交互页面、缺少工作台、主文档替换、旧缓存隔离、同文档/子框架、迟到限制和监听失败/清理。真实 Chrome 离线宿主检查另外执行实际文档切换，验证旧等待释放、新快照独立和访问限制保持；BOSS 网络请求仍为 0。
