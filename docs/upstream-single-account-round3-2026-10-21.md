## 列表与条件共同确认

旧代码应用页面条件后固定等待 1500ms，再检查加载图标是否消失。没有验证实际列表来自当前请求；加载图标缺失也不能证明列表已更新。

现在复用已有响应监视器解码过的数据，不增加网络请求，并共同核对：

1. 实际接口属于当前推荐或搜索来源；搜索词、平台职位类目以及城市和页面条件一致。
2. 页面条件在等待期间保持不变。
3. 页面绑定的职位 ID 顺序与该范围的响应一致，加载指示已结束。

连续分页核对已收到的完整页序列。第一页刷新或条件范围改变会丢弃旧范围缓存；缓存只保留当前范围的 ID 和必要请求参数，不保留整份职位载荷。旧响应正文较晚完成解析时不能覆盖更新的快照，关闭任务时释放快照和分页记录。

真实空响应和空列表一致时可以正常换组合或来源。未能同步时以既有 **100** 暂停并保存进度，明确提示检查列表和网络；确认后的异范围响应以既有 **93** 暂停，保留登录凭证，不触发自动重启。规则按照正文完成解码时的当前范围检查，覆盖“响应头先到、规则启用后正文才到”的窗口。

换源验收 #55 还发现新保护规则的解除时机问题：推荐来源已收集 1 条，切到搜索时仍沿用旧规则，任务以 93 暂停。已修复为切换前解除旧来源规则，确认新列表后重新启用；实际源码片段有回归覆盖，后续 #56 完整轮换通过。#55 的失败记录和检查点证据保留，未计作成功验收。

实现：[列表就绪](../packages/geek-auto-start-chat-with-boss/job-list-ready.mjs)、[响应监视](../packages/geek-auto-start-chat-with-boss/boss-job-responses.mjs)、[核心接入](../packages/geek-auto-start-chat-with-boss/index.mjs)。

## 性能和资源回收

删除条件应用后的固定 1.5 秒等待，按真实状态就绪。用户配置的列表等待、详情阅读、随机输入节奏和周期休息保持原设置。#53、#54、#56 的六次就绪检查分别为 **2、4、4、341、2、1ms**；最终构建 #57 为 **5ms**。这些是条件应用之后的局部确认耗时，不能作为端到端站点吞吐的同比测量。

隔离回归把匹配响应延迟到 2000ms、页面列表延迟到 2200ms；旧的无加载图标判定仍会放行，新实现直到 2200ms 才返回。响应已确认且列表一致时不额外等待 1500ms。

另外修复两条句柄泄漏路径：

- 详情就绪的 `waitForFunction` 返回句柄，确认成功后立即释放。
- 关键词搜索的容器与输入框句柄在成功、输入异常和控件缺失路径均被释放；输入框缺失时明确暂停。

对实际函数进行隔离句柄计数，每种场景执行 1000 次：

| 场景 | 修复前最终持有 / 峰值 | 修复后最终持有 / 峰值 |
| --- | ---: | ---: |
| 连续详情查看 | 1000 / 1000 | 0 / 1 |
| 连续关键词输入 | 2000 / 2000 | 0 / 1 |

前后创建次数相同，收敛来自及时释放；这些是远程句柄计数，不是实际浏览器 RSS 测量。

实现：[详情就绪释放](../packages/geek-auto-start-chat-with-boss/auto-chat-navigation.mjs)、[搜索输入释放](../packages/geek-auto-start-chat-with-boss/search-source.mjs)。
